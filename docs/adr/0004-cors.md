# ADR-0004: Multi-origin CORS via parsed allowlist

- **Status:** Accepted
- **Date:** 2026-07-15
- **Deciders:** Platform team

## Context

The gateway reads `CORS_ORIGIN` from env and applies it via the CORS
middleware. Today the value is treated as a single origin string
(`http://localhost:5173` in dev) and passed straight to the
`origin` option of the `cors` package.

Production reality:

- The frontend may live on `https://app.example.com`.
- The admin console may live on `https://admin.example.com`.
- The marketing site on `https://example.com` may embed a widget
  that calls the public catalog API.
- Local development may want both `http://localhost:5173` and a
  colleague's `http://192.168.1.42:5173` reachable over LAN.

Today any of these scenarios requires either changing the env var,
running a second gateway, or disabling CORS — none of which are
acceptable.

## Decision

We accept a **comma-separated allowlist** in `CORS_ORIGIN` and parse
it into a normalized list of origins. The middleware echoes the
incoming `Origin` header when it matches the allowlist and falls
through to the configured default otherwise.

### Shape

```ts
// config/cors.ts
const raw = process.env.CORS_ORIGIN ?? 'http://localhost:5173';
export const corsOrigins = raw.split(',').map(s => s.trim()).filter(Boolean);
```

### Middleware contract

```
function corsMiddleware(req, res, next) {
  const requestOrigin = req.headers.origin;
  if (requestOrigin && corsOrigins.includes(requestOrigin)) {
    res.setHeader('Access-Control-Allow-Origin', requestOrigin);
    res.setHeader('Vary', 'Origin');
    res.setHeader('Access-Control-Allow-Credentials', 'true');
  }
  // preflight handled by cors package
  next();
}
```

Notes:

- We **echo** the origin rather than reflecting `*` so credentialed
  requests work.
- We set `Vary: Origin` so downstream caches (CDN, browser) don't
  collapse per-origin responses.
- A missing `Origin` (same-origin, server-to-server) is unaffected.
- A disallowed `Origin` gets no `Access-Control-Allow-Origin` header
  and the browser blocks the request — which is the desired
  fail-closed behaviour.

### Configuration examples

```
# dev
CORS_ORIGIN=http://localhost:5173

# multi-tenant dev (colleague on LAN)
CORS_ORIGIN=http://localhost:5173,http://192.168.1.42:5173

# production
CORS_ORIGIN=https://app.example.com,https://admin.example.com
```

### Wildcards and regex

We do **not** support wildcards (`*.example.com`). Each origin is
listed explicitly. This keeps the allowlist auditable and avoids the
subdomain-takeover foot-gun. If we need it later, we add a separate
`suffix:` prefix and require a review.

## Consequences

**Positive**

- Multi-frontend deployments work without code changes.
- Reviewers see exactly which origins are allowed by reading the env
  file.
- Wildcard subdomain attacks are impossible.

**Negative / costs**

- Operators must update env when adding a frontend. This is the cost
  we accept in exchange for safety.
- A long allowlist ships as a long string — we validate it at boot
  (must parse to ≥1 origin, no duplicates).
- The change is **backwards compatible**: a single-origin env value
  behaves identically to today.

**Follow-ups**

- Add a startup log line that prints the parsed origins (redacted)
  on gateway boot so misconfigurations are visible immediately.
- Consider a `/api/v1/admin/cors-origins` endpoint to read the
  active allowlist at runtime — out of scope for this ADR.
